## 13.1 Как читать / Naming and rules

The source text was written against the future schema, so the names differ from the code:

| В тексте / In the source | В системе / In this project |
| --- | --- |
| `reports`, `/api/reports` | `requests`, `/api/requests` |
| `New` | `NEW` («Новая») |

- **Волна** — порядок работ; волна 1 = токены, статусы и отказ с причиной (§13.8).
- Каждый пункт получает ID `BL-*`, новое требование `FR-*`/`NFR-*` и тест-кейсы `TC-*`, чтобы

## BL-T1 — Администратор как управляющий / Admin upgrade

**Цель.** Сейчас администратор только смотрит: список заявок и сводка. Нужен полноценный
управляющий системой.

**Что входит:**

1. **Пользователи.** Список с поиском и фильтром по роли; создание оператора и исполнителя
   (жители регистрируются сами); смена роли; привязка исполнителя к службе (`service_id`);
   блокировка/разблокировка (`is_active`); сброс пароля.
2. **Службы и категории.** Создание, правка, отключение. Если категория или служба уже связана с
   заявками — физически не удаляем, а ставим `is_active = false`, иначе история ломается.
3. **Заявки.** Просмотр всех с фильтрами по статусу, службе, категории и дате; администратор может
   сменить категорию заявки (а значит и службу), если оператор ошибся.
4. **Статистика.** Количество заявок по статусу, по службе и категории, среднее время от «Новой» до
   «Решены», число отклонённых.
5. **Журнал действий (аудит).** Кто, когда и что изменил: роли, блокировки, справочники. Только
   просмотр.
6. **Экспорт в CSV** по текущему фильтру (опционально).

**Ограничения безопасности:**

- администратор не может заблокировать или разжаловать сам себя;
- нельзя убрать роль у последнего администратора;
- все маршруты закрыты `requireRole('ADMIN')` (серверно, как в [07-roles-and-statuses.md](07-roles-and-statuses.md)).

**БД:** `users.is_active`, `users.service_id`, новые таблицы `services`, `categories`
(текущий строковый словарь переезжает в таблицу), `audit_log (id, user_id, action, object, created_at)`.

**API** (пути — в наших терминах):

| Метод | Путь | Кто | Комментарий |
| --- | --- | --- | --- |
| `GET` | `/api/users?search=&role=` | ADMIN | список с фильтрами |
| `POST` | `/api/users` | ADMIN | создать `OPERATOR` / `EXECUTOR` |
| `PATCH` | `/api/users/:id` | ADMIN | роль, служба, активность |
| `POST` | `/api/users/:id/reset-password` | ADMIN | выдать новый временный пароль |
| `GET` / `POST` / `PATCH` | `/api/services`, `/api/categories` | ADMIN | справочники, `is_active` вместо удаления |
| `GET` | `/api/stats` | ADMIN, OPERATOR | расширенная сводка |
| `GET` | `/api/audit?page=` | ADMIN | журнал действий |
| `GET` | `/api/requests/export.csv?…` | ADMIN | CSV по текущему фильтру |

**Экраны:** `/admin/users`, `/admin/categories`, `/admin/services`, `/admin/reports`,
`/admin/stats`, `/admin/audit`.

**Приёмка:**
- администратор создаёт оператора и исполнителя, и они входят под своими ролями;
- заблокированный пользователь получает отказ при входе;
- отключённая категория исчезает из формы жителя, но старые заявки с ней открываются;
- остальные роли на админских маршрутах получают `403`;
- попытка заблокировать себя и снять роль с последнего администратора отклоняется.

**Тесты:** TC-23…TC-27 (см. §13.7).

**Состояние (16.11.2026): реализовано.** Отличия от плана, зафиксированные по факту:

- маршруты живут под `/api/admin/*` (`/users`, `/services`, `/categories`, `/audit`,
  `/export/requests.csv`, `/requests/:id/category`) — так одна проверка `requireRole('ADMIN')`
  закрывает весь блок, а `/admin/stats` остаётся доступна оператору;
- экранов пять, а не шесть: сводка со статистикой, заявки, пользователи, справочники
  (категории и службы на одной странице двумя карточками) и журнал; `/admin/reports` не понадобился;
- `requests.category` остаётся строкой, но проверяется по таблице `categories`; значения из
  `domain.ts` работают как fallback, если справочник пуст;
- справочники связаны кодом: `services.code` = `categories.code`, поэтому «служба заявки» = её
  категория, а исполнитель привязан к службе через `users.service_id`;
- смена категории заявки в работе требует исполнителя новой службы (`400` без него);
  на `NEW` прежний исполнитель снимается автоматически;
- CSV отдаётся с BOM и разделителем `;`, до 5000 строк, тем же фильтром, что и список.

Проверка: `backend/scripts/smoke-admin.ps1` — TC-23…TC-27 и TC-34, результат в
[06-test-cases.md](06-test-cases.md) §10.7.

## BL-T2 — Отказ заявки оператором / Rejection with reasons

**Цель.** Оператор отклоняет дубль, неверную категорию или спам осмысленно, а не «просто
отклоняет». Закрывает открытый вопрос №4 из [08-risks-and-assumptions.md](08-risks-and-assumptions.md).

**Что уже есть в v1:** переход `NEW → REJECTED` только для оператора, обязательный комментарий,
запись в историю в одной транзакции, исполнитель такие заявки не видит, житель видит статус.

**Что добавляется (дельта):**

- фиксированный список причин: «Дубликат», «Не относится к городским службам»,
  «Недостаточно информации», «Спам или некорректное содержание», «Другое» (для «Другое»
  комментарий обязателен);
- поле `requests.reject_reason` (код причины) рядом с существующим `status_history.comment`;
- окно выбора причины в карточке заявки (вместо одного поля комментария);
- причина показывается жителю в «Моих заявках» и в истории;
- необязательная связь `duplicate_of` для дублей (развивается в [BL-O2](#bl-o2--объединение-дублей--merging-duplicates)).

**Открытый вопрос:** исходный текст требует отказ **только из «Новой»**. В v1 разрешён и
`VERIFIED → REJECTED` (оператор может отклонить уже переданную заявку). Предложение: оставить оба
перехода — иначе после передачи заявки отменить её нельзя, — и зафиксировать это в 07. Если нужно
строго по тексту, переход убирается одной строкой в `STATUS_TRANSITIONS` и правилом в
`docs/07-roles-and-statuses.md`.

**Коды ошибок:** отказ без причины — `400`; отказ не из «Новой» — `400` (в v1 недопустимый переход
даёт `409`; привести к тексту задания или оставить `409` и объяснить на защите); не оператор —
`403`.

**Тесты:** TC-10 (без причины → `400`), TC-11 (с причиной → `REJECTED`, история, причина видна
жителю), TC-12 (исполнитель или житель → `403`).

## BL-T3 — Статусы исполнителя / Executor statuses

**Цель.** Дать исполнителю гибкую работу: не только «взял и закрыл».

**Изменения модели:**

- «В работе» → «В процессе» (в тексте: “Rename ‘In progress’ to ‘In progress’”, в русском варианте —
  «В работе» → «В процессе»; окончательная подпись — открытый вопрос);
- новая «Ожидает» (`PENDING`: материалы, техника, согласование, погода);
- «Решена» → «Выполнена» (`RESOLVED` сохраняет код, меняется подпись).

**Разрешённые переходы (v2):**

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| VERIFIED | IN_PROGRESS | EXECUTOR | исполнитель этой службы |
| IN_PROGRESS | PENDING | EXECUTOR | комментарий с причиной обязателен |
| PENDING | IN_PROGRESS | EXECUTOR | **возврат разрешён** — меняет правило «только вперёд» |
| IN_PROGRESS | RESOLVED | EXECUTOR | комментарий необязателен, фотоотчёт желателен |

Остальные переходы запрещены (`400`).

**Правила:** статус меняет только исполнитель той службы, к которой относится категория заявки →
зависит от `service_id` из [BL-T1](#bl-t1--администратор-как-управляющий--admin-upgrade), поэтому
T1 идёт раньше. Житель видит все смены и комментарии исполнителя; на «Выполнена» (и опционально на
«Ожидает») приходит уведомление — [BL-R7](#bl-r7--профиль-и-уведомления--profile-and-notifications).

**Интерфейс:** в карточке только доступные следующие шаги (в «В процессе» — «Приостановить» и
«Готово»); список исполнителя фильтруется по трём статусам.

**Тесты:** TC-13 («Ожидает» без комментария → ошибка), TC-14 (цепочка
`VERIFIED → IN_PROGRESS → PENDING → IN_PROGRESS → RESOLVED`, каждый шаг в истории), TC-15 (чужой
исполнитель → `403`).

**Последствия:** обновить TC-6 и **все** упоминания «Решена» — docs 00, 02, 03, 05, 06, 07, 08,
README, подписи в интерфейсе (`STATUS_LABELS`), слайды 8, 11, 18, 20.

## BL-T6 — Адрес с подсказками и прокси геокодера / Address search + geocoder proxy

`Must`. Меняет основной способ указания места: поле адреса с подсказками вместо «кликни по карте»
(клик остаётся рабочим).

### Провайдер / Provider

- **Photon** — подсказки при вводе; **Nominatim** — обратное геокодирование (клик по карте), либо
  один сервис на оба направления, если предмет это допускает.
- **Перед стартом** проверить актуальные условия использования и лимиты выбранного сервиса.
- Провайдер и лицензия записываются в docs/ (см. §13.4.1), на картах обязательна подпись
  **«© OpenStreetMap contributors»** — уже стоит в `MapPicker`.
- В спринте 3 проверить **15–20 реальных адресов города** на наличие номера дома.

### Серверный прокси / Server-side proxy

| Маршрут | Ответ |
| --- | --- |
| `GET /api/geocode/search?q=…` | до **5** вариантов: `label`, `lat`, `lng` |
| `GET /api/geocode/reverse?lat=…&lng=…` | адрес по координатам |

Оба закрыты `authenticate`, ответы валидируются (числа в диапазонах, `label` — строка до 200 символов).

**Зачем прокси:** единый `User-Agent` и соблюдение лимитов провайдера; кэш повторных запросов
(`GEOCODER_CACHE_TTL`); ключ только в `.env` (`GEOCODER_API_KEY`); возможность сменить провайдера без
правки клиента; частота запросов на пользователя (`GEOCODER_RATE_LIMIT`).

### БД и API

- `requests.address` **уже есть** — текстовая часть адреса переиспользуется; `lat` / `lng` остаются
  главным местом заявки.
- `POST /api/requests` принимает `address` как **необязательное** поле; сервер делает `trim` и
  проверяет длину; **координаты обязательны** (TC-2 не меняется).
- Поиск заявок по адресу уже работает через `?search=` (совпадение по `address`).

### Интерфейс / UI

- Новый `AddressSearch`: поле, подсказки, состояния **loading / ничего не найдено / ошибка**.
- `MapPicker` получает `position` и `onChange`; оба компонента работают через общее состояние формы
  `{ lat, lng, address }`.
- Доступность: `role="listbox"`, подсветка активного пункта, `aria-live` для результатов,
  закрытие по `Esc`, высота пункта не меньше **44 px**.
- На телефоне поле — над картой, подсказки не перекрываются клавиатурой.
- Адрес показывается оператору и исполнителю в карточках и списках.

### Безопасность и приватность

- В README одна строка: адрес отправляется картографическому провайдеру для поиска.
- В запросе к провайдеру **нет** ФИО, email, идентификатора пользователя и токена.
- Запросы к геокодеру не пишутся в лог вместе с персональными данными.
- Ответы провайдера выводятся как **текст**, не как HTML.

### Тесты

TC-16…TC-22 (см. §13.7) и TC-9 (дополнение) — время ответа `/api/geocode/search` с кэшем ≤ **2 с**.

### Приёмка

- выбор адреса перелетает картой, ставит маркер, координаты попадают в заявку;
- клик по карте и перетаскивание маркера обновляют поле адреса;
- ошибки понятны и **не блокируют** создание заявки;
- число запросов к геокодеру ограничено паузой, отменой и кэшем;
- ключи не попадают в репозиторий;
- работает на телефоне и ноутбуке.

## Житель / Resident (1–7)

### BL-R1 — Подтверждение результата и возврат / Confirmation and reopen

`Must`. После «Выполнена» житель видит кнопки «Всё исправлено» и «Проблема осталась». Во втором
случае заявка возвращается оператору — новый переход **`RESOLVED → VERIFIED`** с комментарием и
фото. Закрытая заявка получает итоговую отметку «Подтверждена жителем».

**БД:** `requests.confirmed_at`, `requests.reopen_count`. **API:**
`POST /api/requests/:id/confirm`, `POST /api/requests/:id/reopen`.
**Открытый вопрос:** ограничить число возвратов (`reopen_count ≤ 2`), иначе возможен бесконечный цикл.

### BL-R2 — Оценка и отзыв / Rating and review

`Should`. После подтверждения житель ставит 1–5 звёзд и пишет короткий комментарий; оценки попадают
в статистику администратора и в рейтинг службы.
**БД:** `reviews (id, request_id, rating, comment, created_at)`, `rating 1…5` проверяется на сервере.
**API:** `POST /api/requests/:id/review`. **Тест:** TC-29.

### BL-R3 — Проверка на дубли при создании / Duplicate suggestion

`Should`. Житель ставит точку — система показывает похожие открытые заявки в радиусе ≈50 м той же
категории: «Возможно, такая проблема уже есть. Поддержать?». Снижает поток дублей, которые оператор
отклоняет ([BL-T2](#bl-t2--отказ-заявки-оператором--rejection-with-reasons)).
**API:** `GET /api/requests/nearby?lat=&lng=&category=`.
**Техническая деталь:** в SQLite нет PostGIS, поэтому сначала выборка по «прямоугольнику»
(`lat between … and …`, `lng between … and …` с индексом), затем расстояние по формуле гаверсинуса в
приложении. **Тест:** TC-31.

### BL-R4 — «Мне это тоже важно» / Support votes

`Should`. Житель поддерживает чужую публичную заявку; счётчик повышает приоритет; один голос на
пользователя.
**БД:** `request_votes (request_id, user_id)`, уникальная пара. **API:**
`POST /api/requests/:id/vote`. **Тест:** TC-30.

### BL-R5 — Публичная карта города / Public city map

`Should`. Общая карта всех неотклонённых заявок: цвет маркера по статусу, фильтр по категории.
Без персональных данных — только категория, статус, дата и описание. Может выводиться на лендинге.
**API:** `GET /api/public/requests` — **без токена**, с пагинацией и ограничением полей
(`NFR-3`: публичный ответ не содержит имён, телефонов, e-mail и ссылок на фото с людьми).
**Тест:** TC-28.

### BL-R6 — Черновики, правка и отзыв / Drafts, edit, cancel

`Could`. Черновик формы хранится на устройстве (`localStorage`), пока заявка «Новая» — её можно
править и отозвать. После «Проверена» — нельзя.
**API:** `PATCH /api/requests/:id`, `DELETE /api/requests/:id` — только при `status = NEW` и только
автору. **Тест:** TC-32.

### BL-R7 — Профиль и уведомления / Profile and notifications

`Could`. Правка ФИО, смена пароля, настройка уведомлений (все смены статуса или только
«Выполнена»). Счётчик непрочитанных и колокольчик в шапке закрывают FR-5 целиком.
**БД:** `notifications (id, user_id, request_id, text, is_read, created_at)`. **API:**
`GET /api/notifications`, `PATCH /api/notifications/:id/read`. **Тест:** TC-33.

## Оператор / Operator (1–8)

### BL-O1 — Приоритет заявки / Priority

`Must`. Оператор ставит приоритет: низкий, обычный, высокий, **срочный** (открытый люк, оборванный
провод). Исполнитель видит заявки, отсортированные по приоритету.
В v1 поле `priority` уже есть (`LOW | NORMAL | HIGH`) — добавляется значение `URGENT`, элемент
управления в карточке, сортировка в списке исполнителя и подпись в `PRIORITY_LABELS`.

### BL-O2 — Объединение дублей / Merging duplicates

`Must`. Вместо простого отказа оператор связывает дубль с основной заявкой
(`duplicate_of`), жители всех дублей получают уведомления о статусе основной.
**БД:** `requests.duplicate_of`. **API:** `POST /api/requests/:id/merge { targetId }`.
**Открытый вопрос:** что видит житель дубля — статус основной заявки или пометку «объединена с №N».

### BL-O3 — Режим «Список / Карта» / Map mode with clusters

`Should`. Переключатель в очереди оператора: маркеры новых заявок, кластеры при большом количестве —
скопления проблем видны сразу. В `GET /api/requests` добавляется агрегированный режим
(`view=map`) или отдельный `GET /api/requests/clusters?bbox=`.

### BL-O4 — Шаблоны ответов / Reply templates

`Should`. Готовые тексты для причин отказа и комментариев; оператор выбирает и при необходимости
правит. **БД:** `reply_templates (id, title, text)`; управляет администратор (часть BL-T1).
**API:** `GET /api/templates`.

### BL-O5 — Внутренние заметки / Internal notes

`Should`. Комментарии, видимые только сотрудникам (оператор, исполнитель, администратор); нужны для
передачи контекста между сменами. **БД:** `internal_notes (id, request_id, author_id, text, created_at)`.
**API:** `GET` / `POST /api/requests/:id/notes` (роли `OPERATOR`, `EXECUTOR`, `ADMIN`; жителю — `403`).

### BL-O6 — Контроль сроков / SLA and overdue

`Should`. Для каждой категории задаётся целевое время (например, «яма» — 7 дней, «фонарь» —
3 дня); просроченные подсвечиваются красным, на дашборде оператора — счётчик «Просрочено».
**БД:** `categories.sla_hours`. **API:** `GET /api/requests?overdue=true`; вычисление —
`createdAt + sla_hours < now()` и статус не финальный.

### BL-O7 — Массовые действия / Bulk actions

`Could`. Выбор нескольких заявок и одно действие: «Проверена», смена приоритета, отказ с одной
причиной. **API:** `POST /api/requests/bulk { ids, action, payload }` — всё в одной транзакции,
частичный успех не допускается.

### BL-O8 — Личный дашборд / Personal dashboard

`Could`. Сводка за день: сколько новых, сколько обработано мной, средняя скорость обработки.

### BL-T4+ — (перенесено)

Подсказки адреса и обратное геокодирование выделены в отдельную задачу
[BL-T6](#bl-t6--адрес-с-подсказками-и-прокси-геокодера--address-search--geocoder-proxy).

## 13.5 Матрица статусов v2 / Status matrix v2

`docs/07-roles-and-statuses.md` после волны 2 выглядит так (новое выделено):

| Из | В | Кто | Условие |
| --- | --- | --- | --- |
| NEW | VERIFIED | OPERATOR | выбран исполнитель службы |
| NEW | REJECTED | OPERATOR | причина из списка (+ комментарий для «Другое») |
| VERIFIED | IN_PROGRESS | EXECUTOR | исполнитель службы заявки |
| IN_PROGRESS | PENDING | EXECUTOR | **новый**, комментарий обязателен |
| PENDING | IN_PROGRESS | EXECUTOR | **новый**, обратный переход разрешён |
| IN_PROGRESS | RESOLVED | EXECUTOR | комментарий необязателен, фотоотчёт желателен (`photos.kind = RESOLUTION`) |
| IN_PROGRESS | VERIFIED | EXECUTOR | **новый**: вернуть оператору (нужна другая служба) |
| PENDING | VERIFIED | EXECUTOR | **новый**: вернуть оператору |
| RESOLVED | VERIFIED | RESIDENT | **новый**: «Проблема осталась», комментарий + фото, `reopen_count++` |
| RESOLVED | — | RESIDENT | отметка «Подтверждена жителем» (`confirmed_at`), не отдельный статус |

Подписи после переименования: `IN_PROGRESS` — «В процессе», `PENDING` — «Ожидает»,
`RESOLVED` — «Выполнена».

`REJECTED` остаётся финальным: исполнитель такие заявки не видит, житель может создать новую, но не
возобновить отклонённую.

| **1** | BL-T5 (токены), BL-T3 (статусы), BL-R1 (подтверждение/возврат), BL-O1 (приоритет), BL-T2 (отказ с причинами) | задано явно: дизайн-токены, статусы и БД/API — на них висит всё остальное |
| **2** | BL-T4 (лендинг на готовых стилях) + BL-T6 (адрес и карта) вместе с формой заявки | лендинг опирается на токены, `AddressSearch` живёт в форме заявки |
| **3** | BL-T1 (админка), статистика, экспорт CSV, BL-R2 (оценки), BL-O8 (дашборд) | админка зависит от `service_id`, `categories` и новых статусов — поэтому последняя |
| **4** | остальные пункты по ролям из таблицы MVP | по остатку времени |

> Это отменяет прежний порядок «админка вперёд»: зависимость важнее.

**Не входит** (зафиксировано в [02-requirements.md](02-requirements.md) §4.3): мобильное приложение,
Telegram-уведомления, внешняя аналитика.

## 13.9 Риски / Risks

| Риск | Последствие | Что делать |
| --- | --- | --- |
| Переименование статусов («Решена» → «Выполнена», «В работе» → «В процессе») | расхождение интерфейса, документов и слайдов | одна волна, один коммит, обновить TC-6 и все упоминания по списку в BL-T3 |
| Правило «только вперёд» ломается переходом `PENDING → IN_PROGRESS` | старые тесты и матрица 07 устаревают | матрица v2 (§13.5) становится единственным источником, `STATUS_TRANSITIONS` обновляется вместе с ней |
| Отказ только из «Новой» vs уже разрешённый `VERIFIED → REJECTED` | либо регресс процесса, либо расхождение с текстом | решить до волны 1, записать в 08 (открытые вопросы) |
| Справочники переезжают из строки в таблицу | риск потерять историю старых заявок | три шага миграции (§13.3), `category` не удалять |
| Публичные маршруты без токена | утечка персональных данных | NFR-3: белый список полей, пагинация, лимит частоты, тест TC-28 |
| Геокодер (BL-T6) | внешний провайдер недоступен: форма встаёт | таймаут 3–5 с, кэш, лимит частоты, деградация до ручной точки (TC-21); ToS проверены до старта |
| Объём бэклога (21 пункт) | не влезает в один спринт, демо размывается | волны, каждая заканчивается демо и обновлением тест-кейсов |

## 13.11 Открытые вопросы / Open questions

1. Отказ: разрешать ли `VERIFIED → REJECTED` (рекомендация — да, с записью в 07).
2. Сколько раз житель может вернуть заявку (`reopen_count`): 1, 2 или без ограничения.
3. «Подтверждена жителем» — отметка (`confirmed_at`) или отдельный статус; рекомендация — отметка.
4. Геокодер: два сервиса (Photon для подсказок, Nominatim для обратного) или один на оба
   направления.
5. `GEOCODER_CACHE_TTL` и `GEOCODER_RATE_LIMIT` — конкретные значения после проверки ToS.
6. Обязателен ли текст адреса в форме: сейчас координаты обязательны, адрес — нет; в задании адрес
   тоже опциональный.
7. Что видит житель дубля после объединения: статус основной заявки или «объединена с №N».
8. Экспорт CSV — в волне 3 или отложить.
9. Остаток текста задачи 4 (лендинг обрезан) — нужны блоки и тексты.
